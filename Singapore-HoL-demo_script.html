S1
Opening — The Energy Problem
⏱ 2 min
● ON SCREEN
  • ▶Nothing running yet. Keep the Cloudera AI dashboard visible in the background.
● TALKING POINTS
  • 5G base stations account for roughly 70–80% of a mobile operator's energy bill. Most sites are over-provisioned — all cells active regardless of whether there's traffic to serve.
  • Traditional energy saving is rule-based: "sleep cell X between 2 AM and 6 AM." That breaks the moment traffic patterns shift or the operator changes their QoS target.
  • What we're showing today is a different approach: the operator states intent — "keep QoS above 5 Mbps" — and the system figures out which cells to sleep or wake, in real time, autonomously.
  • No static schedules. No manual tuning. Two LLMs collaborating with VIAVI's network simulator to make safe decisions every 15 minutes.
"You tell it what you care about. It handles the how."
● KEY MESSAGE
Intent-based automation replaces static rules. The operator sets the QoS floor; the closed loop optimizes energy within it — continuously.
S2
Architecture — How the System Works
⏱ 3 min
● ON SCREEN
  • ▶Draw or narrate the flow. You can sketch on a whiteboard or talk through it verbally while pointing at the Cloudera AI dashboard.
  • ▶If you have a slide with the architecture diagram, show it here.
● TALKING POINTS
  • Cloudera AI hosts two LLM endpoints on-prem: a Qwen3-Coder-30B (the Planner — richer reasoning) and a Qwen2.5-Coder-7B (the Validator — faster). Both run on AWS g5 GPU instances managed through Cloudera's model serving runtime.
  • VIAVI AI RSG is the network simulation engine. It models a 7-site, dual-band (700 MHz + 2100 MHz) 5G network. When we say "sleep a cell," we're commanding a real simulator — not a spreadsheet.
  • The closed loop runs every 15 simulated minutes:
    ① Planner LLM analyses baseline KPIs via SQL, generates Sleep/Wake recommendations
    ② RSG Sim #1 tests the Sleep recommendations under the next traffic profile
    ③ Validator LLM approves or rejects each recommendation based on Sim #1 results
    ④ RSG Sim #2 applies approved actions and reports final KPIs
  • The two-simulation safety gate is the key insight: Planner proposes, Validator verifies with actual simulation data before any action is committed.
  • All data — model weights, KPIs, decisions — stays within the Cloudera environment. Nothing leaves.
● KEY MESSAGE
Two LLMs, two simulations, one safety gate. No cell is put to sleep unless simulation confirms QoS holds. That's the architecture's guarantee.

● TALKING POINTS
  • Both models are deployed via Cloudera AI Inference Service — built on KServe with vLLM underneath. They expose an OpenAI-compatible REST API, which is why the notebook uses LangChain's ChatOpenAI class — the client is identical regardless of which model is behind the endpoint.
  • The 30B is a Mixture-of-Experts model — 30B total parameters but only 3B active per token. Large reasoning capability, manageable inference cost. It runs across 3 A10G GPUs using tensor parallelism.
  • The 7B is the faster model. We can use it to show the latency difference — it responds roughly 3–4× faster but produces less nuanced SQL on multi-site reasoning tasks.
  • Swapping models is a one-line change in .env — CDSW_API_URL points to whichever endpoint you want. That's the value of a standard API contract.
● KEY MESSAGE
Enterprise LLM serving on-prem: GPU-accelerated, OpenAI-compatible, swap-ready. The network never sees an external API call.

Anticipated Q&A

What happens if the LLM makes a bad recommendation?
The Validator is the safety net. Before any Sleep command is committed to the network, RSG Sim #1 runs with that command applied and returns live KPI data. If average QoS at any site drops below the operator's threshold, the Validator rejects that specific recommendation. The cell stays on. Only if simulation confirms QoS is maintained does the Sleep go through. The LLM can propose anything — the simulator enforces reality.
Is this using real network data?
The baseline KPIs (UEReports.csv, CellReports.csv) are representative 5G network traces. The live simulation is VIAVI AI RSG — a high-fidelity 5G network simulator modelling real antenna patterns, UE mobility, PRB allocation, and energy profiles. The sleep/wake commands we send are the same RIC control primitives used in production O-RAN deployments.
Can we use a different LLM — our own model or a different provider?
Yes — the system uses an OpenAI-compatible REST API. Changing the LLM is a two-line edit in .env: set CDSW_API_URL to any endpoint that speaks the OpenAI chat completions format, and update the key. We've tested with Cloudera-hosted Qwen, NVIDIA NIM endpoints, and OpenAI directly. The LangChain ChatOpenAI client handles all three identically.
What's the difference between the 30B and 7B models in practice?
Latency: The 7B responds 3–4× faster (lower TTFT, higher tokens/sec on a single A10G). Quality: The 30B produces more accurate multi-site SQL — it handles correlated conditions across sites in one query. The 7B sometimes simplifies the query structure and misses edge cases at high-load or mixed-traffic sites. For a production deployment, the 30B is the better Planner; the 7B is a good Validator or fallback when the 30B is busy.
How does the VIAVI connection work technically?
The VIAVI ADK (Python wheel) is downloaded directly from the RSG at runtime — pip install http://<rsg-host>:8000/adk. Each user gets a dedicated container on the RSG, identified by a SHA-256 hash of their public IP and username, so sessions are isolated even in a 20-person lab. Commands (turn_off, turn_on) go over HTTP to the container's REST API. Simulation results come back as Pandas DataFrames via the same connection.
Could this run in production against a live RAN?
This PoC uses VIAVI RSG as a digital twin standing in for a live RAN. In a production path, RSG Sim #1 and Sim #2 would be replaced by calls to the actual RIC (O-RAN near-RT RIC) — the LLM Planner and Validator remain unchanged. The architecture is designed so the simulation layer is swappable. VIAVI's RSG is specifically valuable here because it supports the same E2 interface and RIC control primitives as production O-RAN deployments.
What if the RSG returns a 429 rate limit error?
The code handles this automatically. When the RSG returns 429, it includes a cooldown_remaining_seconds field. The notebook reads that value, waits the exact cooldown period plus a 10-second buffer, then retries. You'll see a message like "RSG quota exceeded. Waiting 70s then retrying." In a multi-user lab, stagger the start times by 2–3 minutes to avoid all participants hitting the RSG simultaneously.
